# Flutter scaffold contract

Read this when preparing intake and implementing the foundation. The names below are this skill's conventions, not a mandatory official Flutter layout. Adapt to explicit user choices while preserving responsibilities.

## Lean foundation to offer

A foundation organized by feature, with native navigation, local state, and a centralized theme. Do not add state/routing/network packages for convenience; preserve dependencies required by the installed SDK's template, including design packages when used by that template.

Localization and Material/Cupertino differ across versions. Check template imports and available APIs: SDKs using separate design packages must not receive incompatible imports from older examples. For an SDK using `package:flutter/material.dart`, configure `flutter_localizations` when necessary. Do not migrate the SDK or import family during scaffolding without an authorized need.

This foundation does not determine colors, fonts, platforms, or identifiers. Those come from intake. If the user wants Riverpod, Bloc, GoRouter, or another solution, initialize that choice and adapt the scaffold; do not install multiple alternatives.

## Base structure

```text
lib/
  main.dart
  app/
    app.dart
    config/
      app_config.dart
    router/
      app_router.dart
    theme/
      app_colors.dart
      app_theme.dart
      app_typography.dart
      app_spacing.dart
  shared/
    widgets/
      app_button.dart
      app_text_field.dart
      app_scaffold.dart
  features/
    home/
      presentation/
        home_page.dart
test/
  app_test.dart
  shared/
    widgets/
      app_button_test.dart
      app_text_field_test.dart
```

The app's technical README belongs to both delivery modes. `docs/bootstrap.md`, agent directories, and agent instructions depend on the explicit intake choice; they are not required parts of the structure above.

Add `assets/images/` and `assets/fonts/` when actual resources exist. If the user wants empty directories tracked in Git, use `.gitkeep` and explain its purpose; do not register fictitious images or fonts in `pubspec.yaml`.

Create `data/`, `domain/`, `providers/`, or `view_models/` directories when the selected architecture or an implemented component justifies them. Do not fill every feature with empty base classes, repositories, or services.

## Initialization, configuration, and navigation

- `main.dart`: minimal initialization and `runApp`; asynchronous initialization only when needed.
- `app.dart`: root widget receiving configuration, composing `MaterialApp` or `MaterialApp.router`, and connecting themes, language, and navigation.
- `app_config.dart`: centralized typed configuration, display name, and selected environment options. Prefer injection into the app over mutable global settings. Compiled definitions are public configuration for project purposes; do not store secrets in the client.
- When environments are included, document `--dart-define` keys and example values. Validate a required URL with a clear message before use. Without a selected API, the app must start without extra configuration or a fictitious endpoint.
- `app_router.dart`: single entry point for implemented routes. For the lean foundation, a native initial route connected to Home is enough. Do not create unrequested login/settings screens or buttons targeting nonexistent routes.
- Language: `locale`, `supportedLocales`, and delegates must match intake. For multiple languages, configure localization generation and use generated messages rather than scattered hardcoded text. Do not introduce files depending on an undocumented generation step.

If the generator requires a fallback ARB for a regional locale, provide the corresponding base resource, such as `en` for `en_US`, and check resolution of the selected locales. Do not remove the requested regional variant just to bypass the generator error.

Keep these concepts separate:

- Display name: user-facing title; spaces and accented characters are valid.
- Technical name: Dart package name, imports, and project name.
- Organization/IDs: Android, Apple, and other platform identifiers as generated by the template. Do not promise identical technical-name transformations across platforms; inspect the generated files.

Update visible metadata for each selected platform: for example, the Android label, Apple display name, web title/manifest, and desktop runner names/titles. Inspect the installed SDK's templates. Do not change chosen IDs merely to change a display title. The initial screen's logo and the application icon are separate resources; configure each only when requested and suitable assets exist.

## Theme and visual identity

- `app_colors.dart`: explicit brand colors and selected light/dark color schemes. Use `ColorScheme.fromSeed` when palette derivation is authorized. If the primary color must be exact, preserve it and check contrast with `onPrimary`; seed generation can produce a different tone.
- `app_typography.dart`: selected font family and semantic text styles. Use `TextTheme` roles such as titles and body text instead of repeating sizes and colors across screens.
- `app_spacing.dart`: a few reused spacing values, without a speculative token catalog.
- `app_theme.dart`: compose necessary `ThemeData` instances and global styles for used components, including buttons, fields, app bars, and surfaces. Connect `theme`, `darkTheme`, and `themeMode` according to the answer; “both” must resolve whether to follow the system or use a selector. Use theme types compatible with the SDK rather than deprecated APIs from another template.
- Widgets and pages consume `Theme.of(context)` and shared tokens. Check readability, focus, disabled states, and text scaling.

Fonts:

- System font: do not declare an unavailable family or add a font package.
- Custom font: obtain real files, include only available weights/styles, and register them in `pubspec.yaml`. Do not create fictitious font files.
- Catalog font: check the official source, license, and compatibility. Prepare local assets for used weights when offline operation is expected; do not leave the first launch dependent on an unnoticed font download.

## Working shared widgets

Create the following three base widgets. Common styling belongs in the theme; wrappers add behavior or composition used by the project.

| Widget | Expected behavior |
| --- | --- |
| `AppButton` | Text/child, callback, disabled state, and loading state. While loading, show progress with a localizable accessibility label and prevent another activation. Do not hardcode a language inside the shared wrapper. Consume the button theme. |
| `AppTextField` | Wrap `TextFormField` with a label, external controller, validation, and necessary keyboard/obscuring options. Respect controller ownership: do not dispose of a controller received from the caller. Consume the field theme. |
| `AppScaffold` | Compose a common page structure with an optional title, `SafeArea`, spacing, and a flexible body. Support scrollable content without incompatible size constraints. |

Feature-specific widgets belong in `features/<name>/presentation/widgets/`. Shared loading, empty, and error states can be added when scoped or actually used. Do not create an entire design system unnecessarily.

## Initial screen

Replace the template counter with a Home screen using the chosen identity and an adaptive layout. Use the shared components in a small, honest interaction, such as a demonstration form with validation and local feedback. Identify it as a development example; do not present it as persisted data or a service integration.

Do not put infrastructure notices into the product flow. Directory, architecture, and command instructions belong in developer documentation.

When no features are specified, do not invent registration, authentication, dashboards, or business data. Keep the initial screen simple and easy to replace with the first actual feature.

## Optional agent setup and documentation

In **scaffold-only mode**, keep essential technical documentation in the README: how to run, validate, and start a feature, plus where to change the theme and configuration. Do not create `docs/bootstrap.md`, memory files, histories, skills, or AI directories.

In **agent-setup mode**, follow the agent and conventions resolved during intake. Possible artifacts include a project-specific `AGENTS.md`, directories recognized by the chosen agent, and a context document. These examples are not an automatic creation checklist. Do not copy this skill's `agents/`, `references/`, or `tools/` directories into the app or mirror the user's personal installation. If skills were explicitly selected, copy only those, preserving their licenses and excluding personal data.

Do not modify existing agent files merely to match a new delivery mode. If updating one is in scope, preserve its contents and applicable instructions.

When `docs/bootstrap.md` is included in the accepted setup, record:

- Resolved intake: identity, purpose, platforms, palette, font, language, stack, and environments.
- Where to change themes, components, routes, and configuration.
- How to add a feature following the chosen organization.
- Actual dependency, run, analysis, test, and supported-build commands, including environment definitions when used.
- Verification coverage and actual host limitations.

Without this document, report decisions and verification evidence in chat, while keeping durable commands and usage guidance in the README.

Avoid infrastructure TODOs required for startup. Outstanding product features can be documented as next development work.

## Observable acceptance criteria

1. Dependencies resolve and the initial route opens without requiring an API that was not chosen.
2. Display name and identifiers match intake, including selected platforms' metadata.
3. Theme and typography are connected to the real widget tree; requested modes render correctly.
4. The initial route resolves to Home and shared widgets work: field validation, button callback, and blocking during loading.
5. No imports, assets, fonts, or routes point to nonexistent files.
6. Formatting, analysis, and tests pass. At least one chosen platform builds when available infrastructure permits it.
7. The developer has enough instructions to run the app and start the first feature.
8. New files match the chosen mode: without agent setup, no AI artifacts were created; with setup, only agreed files were created and existing files were preserved.

Tests must observe these behaviors. Do not only test filenames, directory existence, or documentation wording. Consult the [verification matrix](verification.md) for commands, coverage, and evidence reporting.
